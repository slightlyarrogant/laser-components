# LC Connect — full audit (2026-09-15)

Scope: security/auth, memory/perf/reliability (measured), multi-tenancy readiness, drift vs VendoConnect, open beads.
Method: four parallel read-only audits + a 300–900-session load test against an isolated instance on :3113 (live :3003 untouched).
Live baseline: pid 38200, uptime 7d21h, RSS 57 MB, 28 fds, 0 restarts.

## 0. Active incidents (not "findings" — things broken today)

1. **OAuth client registry is empty → customer connector cannot refresh.** `dynamic_clients.json` / `refresh_tokens.json` resolve to `process.cwd()` (`src/auth/oauth.ts:73,144`). The repo was re-cloned on 2026-09-07 16:36 (reflog: clone from github), both files were lost, and the process started with an empty registry. `server.log` shows `POST /token → 401` ×3 then `GET /authorize → 400` ×3 = `unauthorized_client`. Access tokens (24 h JWT, signature-only check) still work until expiry; after that the client is locked out until the user removes and re-adds the connector.
2. **`report_issue` always fails.** `WHATSAPP_URL` is not in `.env`; default is `http://localhost:8092` (`src/config.ts:33`, `src/tools/report.ts:15`). Live bridge is 3092 (`curl :3092/health` = connected; :8092 = dead).
3. **Admin credentials are public.** `demo/presentation/landing/index.html:307-308` prints `test@lasercomponents.local / Test1234!`; that user is seeded `role: ADMIN` (`scripts/seed-test-user.ts`). `/demo` is unauthenticated. Combined with §1-C2 below this means: anyone who finds the URL can read every lead and call `delete_lead` / `delete_product` / `batch_update_leads`.

## 1. Security

**Critical**
- C1 public admin creds (above).
- C2 **no authorization inside any tool.** Every handler does `void getTenantSub();` and discards it (e.g. `src/tools/leads.ts:88,196,284,372,467,582,719,818,950`; same in products/applications/ai/knowledge/analytics). `UserRole` exists in `prisma/schema.prisma:15` but is never read. Ungated destructive tools: `delete_lead` (leads.ts:344), `delete_product` (products.ts:382), `batch_update_leads` (leads.ts:906, 500 ids via `updateMany`), `batch_create_leads`, `update_resource`/`create_resource` (knowledge.ts:551,604).
- C3 **PKCE advertised, not enforced; redirect_uri never validated.** `code_challenge_methods_supported: ["S256"]` is published (oauth.ts:292, index.ts:84) but `code_challenge`/`code_verifier` do not appear in the codebase. `/register` (oauth.ts:302-324) echoes `redirect_uris` without storing them; `/authorize` only checks presence (oauth.ts:338); token endpoint auth is `none`. Attack: register a client, send victim `/authorize?...&redirect_uri=https://evil/cb`; the server renders the real login form and 302s the code to the attacker (oauth.ts:399-402) → full 24 h token.

**High**
- H1 `/session-log` + `/session-log/stream` are public (index.ts:175-203) and stream every tool call plus live authorize URLs (client_id, redirect_uri, state).
- H2 JWT: no `aud`, issuer check skipped (oauth.ts:201-206), no `jti`/revocation, 24 h TTL (config.ts:24). Secret min length 16 — the `.env.example` placeholder would pass. (Live secret verified 64 chars, not the placeholder.)
- H3 No rate limiting, no body limit anywhere. `POST /authorize` is an unthrottled bcrypt(12) oracle on a public URL (~250 ms CPU per attempt, single thread).
- H4 `/datasets/:id.csv` serves lead PII without a bearer check (index.ts:228; datasets.ts:181), 12-hex handle, 4 h TTL, `Access-Control-Allow-Origin: *`.

**Medium**
- M1 OAuth state in memory/JSON files, written `writeFileSync` on the request path on every login (oauth.ts:98,158); `authCodes` uncapped; `POST /register` unauthenticated and the client Set never expires (trivial disk/memory growth loop).
- M2 Perplexity (ai.ts:68) receives lead names/websites (`enrich_lead`, ai.ts:466-479) and pipeline aggregates (`generate_insights`) with no timeout.
- M3 `report_issue` dead bridge (above); `title`/`description` have no `.max()` (report.ts:63-68); raw fetch error echoed to the model (report.ts:139).
- M4 systemd unit has zero hardening: runs as `bogdan` with access to `~/.ssh`, `~/.hermes/.env`, ngrok authtoken; no `NoNewPrivileges/ProtectHome/ProtectSystem/ReadWritePaths`.

**Low**: `get_leads` has no limit cap (leads.ts:68); CORS `*` with Authorization allowed (index.ts:46-60); raw Prisma error text to the model (leads.ts:868); `status.toUpperCase()` unvalidated (leads.ts:487). Deps: hono 4.12.21 carries 15 advisories (relevant: CORS reflect-any-origin-with-credentials, CORS ReDoS, parseBody memory exhaustion) — `npm audit fix` → 4.13.8. `ip-address`/`qs` highs come via the MCP SDK's express dependency, which this Hono server never loads.

**Done well**: no raw SQL, no eval/child_process; zod on every tool; enums for sortBy/orderBy; batch caps 200/500; identical login error for unknown-user vs bad-password; bcrypt cost 12; auth codes single-use 300 s; refresh tokens rotate; login form HTML-escaped; `stripSensitive()` on every widget row/CSV; `/demo` path-traversal guard correct; config zod-validated, fails closed; git history clean of secrets; `.env` 0600.

## 2. Memory, performance, reliability (measured)

**There is no leak in production.** Stateless server: `sessionIdGenerator: undefined` (index.ts:336) → no session map, DELETE is a no-op, 300 sessions with/without DELETE identical. fds flat across ~2500 requests. Both `setInterval`s are module singletons and `.unref()`'d. Session log is a 500-entry ring buffer.

Retention ledger (RSS after ≥30 s idle): 600 sessions with `get_leads(200)` → +83 MB; 300 sessions without → +0 MB; 900 pings + 500 SSE open/abort → +0 MB. **The only thing that retains memory is the dataset store.**

- P1 **`datasets` Map is unbounded** (datasets.ts:36): 4 h TTL, `prune()` only runs on write, no max count/bytes. ~320 KB per `get_leads` result at 396 rows; at 10 k leads 300 calls ≈ 2.4 GB vs `MemoryMax=infinity`. And it double-holds: `okList` (datasets.ts:244-258) already ships every row inline in `_meta.rows`; the store only backs a CSV button.
- P2 **No `process.on(...)` at all** — no unhandledRejection/uncaughtException/SIGTERM, no `prisma.$disconnect()`. On Node 22 an unhandled rejection is fatal; `Restart=on-failure` catches it but kills in-flight requests. (A throwing tool does NOT crash the process — verified: returns `isError` / -32602.)
- P3 **No timeout/AbortController on any outbound fetch** (ai.ts:68, report.ts:109).
- P4 **New McpServer per HTTP request** (index.ts:335-344 → server.ts:72): 45 registrations + 6 widget resources each time; measured ~580 KB garbage/request, `tools/list` = 66.7 KB. Not a leak (fully reclaimed) but sets a high floor: 50-way burst of `get_leads(400)` peaked at 679 MB RSS, ~130 req/s, 0 errors. Transport/server never `close()`d (index.ts:341).
- P5 Unbounded `findMany` + whole-result `JSON.stringify` in `export_data` (ai.ts:949/959/968); `search_resources` loads every Resource with full content and scores in JS (knowledge.ts:111-124).
- P6 `GET /mcp` SSE sends zero bytes ever — no keep-alive; ngrok drops silent streams. `/session-log/stream` cleans up on abort but `logEmitter` has no `setMaxListeners` (warns at 11 viewers).
- P7 `Lead` has zero `@@index`; live DB has only pkeys on `leads`/`notes`. Measured irrelevant at 396 rows; revisit past ~50 k.

## 3. Multi-tenancy

Current state: **zero tenant scoping, 42/42 tools discard `getTenantSub()`.** Plumbing is correct (AsyncLocalStorage in server.ts:17-27, populated from the JWT at index.ts:317,338). No tenant/org table (`Organization` is a lead's employer). `User` has no tenant FK. `Lead.createdByUserId` exists but is never written. `Note.user_id` is caller-supplied (spoofable). Perplexity key and WhatsApp recipient are global (recipient hardcoded to Bogdan's JID, report.ts:16). Only 13 of 27 models are touched by the connector — that is the real migration surface.

**Recommended: shared schema + `tenant_id` + Prisma client extension** that injects `where.tenantId` / `data.tenantId` from the request context for all non-global models. Schema-per-tenant multiplies pools and migrations; process-per-tenant multiplies an already hand-managed deploy. With the extension, forgetting a filter in tool #43 is impossible by construction.

Checklist: (1) `tenants` table + `tenant_id NOT NULL` + index on users, leads, notes, products, categories, subcategories, applications, product_applications, score_overrides; backfill to tenant 1. Global: regions, countries; resources two-tier (`tenant_id NULL` = provider playbook). learning_events tenant-owned. (2) `db/client.ts` `$extends` (~60 lines); `server.ts:17` context → `{userId, tenantId, tenant}`; `oauth.ts:181-199` add `tid` claim, carry through refresh grant; `index.ts:338` run with resolved tenant; per-tenant Perplexity client (ai.ts:87-95) and WhatsApp recipient; datasets stamped with owner + bearer on the CSV route. (3) DCR client stays a transport detail; tenant settled at login from the user row. (4) `scripts/onboard-tenant.ts <slug> <admin-email>`. (5) Two-tenant isolation test as the gate. **Effort 6–9 days** (+3 if the deploy story moves in the same pass).

Open question for the decision: "multi-tenant" = many *companies* (each their own leads/products) or many *users at Laser Components* (one company, per-user ownership + roles)? The second is ~2 days (role gating + createdBy scoping), not 6–9.

## 6. Proposed plan (draft — to be confirmed into to-do.md)
